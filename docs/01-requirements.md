# 校园班车预约平台需求说明书

> 文档版本：v0.1  
> 文档状态：需求基线草案  
> 项目代号：School Bus Platform  
> 本阶段目标：先定义可验证的业务闭环，暂不讨论具体代码实现。

## 1. 项目背景

学校有两个校区，学生需要在固定时间乘坐校区间班车。人工登记或简单表单存在以下问题：

- 学生无法实时查看班次和剩余座位。
- 高峰期多人同时预约，可能发生重复占座或超卖。
- 未付款订单长期占用座位，影响其他学生预约。
- 支付、取消和座位释放之间容易出现状态不一致。
- 管理员缺少统一的车辆、路线和班次维护入口。

本项目提供班次查询、在线选座、订单创建、模拟支付和超时取消能力，并以“不超卖、可追踪、可恢复”为核心目标。

## 2. 项目目标

### 2.1 业务目标

- 学生能够完成“登录 → 查班次 → 选座 → 下单 → 支付 → 查订单”的完整流程。
- 管理员能够维护车辆、路线和班次。
- 待支付订单超过 15 分钟后自动取消并释放座位。
- 并发预约时，同一班次的同一座位最多只能属于一个有效订单。

### 2.2 学习与面试目标

- 能解释为什么先实现单体业务闭环，再拆分微服务。
- 能解释数据库事务、唯一约束、幂等、缓存和消息最终一致性的职责边界。
- 能通过自动化测试证明系统不会超卖，而不是只在简历中描述。
- 能演示消息重复、服务重启和支付通知重复等异常场景。

## 3. 用户角色

### 3.1 学生

- 注册和登录。
- 查询可预约班次。
- 查看班次座位图。
- 选择一个座位并创建订单。
- 对待支付订单进行模拟支付。
- 主动取消待支付订单。
- 查询自己的订单及状态。

### 3.2 管理员

- 创建和维护车辆。
- 创建和维护校区间路线。
- 发布、修改和停用班次。
- 查询班次预约情况。

## 4. MVP 功能范围

### 4.1 账户与认证

- 学生使用学号和密码注册。
- 学号在系统内唯一。
- 密码必须经过安全哈希后保存，禁止明文存储。
- 登录成功后返回访问令牌。
- 普通学生不能调用管理员接口。

### 4.2 车辆与路线

- 车辆包含车牌号、座位数和启用状态。
- 车牌号在系统内唯一。
- MVP 默认每辆车有 50 个座位，座位编号为 `1` 至 `50`。
- 路线包含出发校区、到达校区和预计行驶时间。
- 出发校区和到达校区不能相同。

### 4.3 班次

- 管理员选择车辆、路线和发车时间创建班次。
- 已停用车辆不能用于发布新班次。
- 同一车辆在时间重叠的区间内不能安排多个班次。
- 学生只能查询处于可预约状态且尚未发车的班次。
- 班次展示发车时间、到达校区、票价和剩余座位数。

### 4.4 座位预约

- 学生进入班次详情后可以查看座位状态。
- 座位状态分为：

| 状态 | 含义 |
|---|---|
| `AVAILABLE` | 可以预约 |
| `LOCKED` | 已被待支付订单临时占用 |
| `SOLD` | 已支付，不可再预约 |

- MVP 中一个学生对同一班次最多预订一个座位。
- 创建订单成功后，座位进入 `LOCKED` 状态。
- 支付成功后，座位进入 `SOLD` 状态。
- 订单取消或超时后，座位恢复为 `AVAILABLE`。

### 4.5 订单

- 创建订单前必须再次验证班次和座位状态。
- 订单号在系统内全局唯一。
- 订单记录用户、班次、座位、金额和过期时间。
- 订单状态分为：

| 状态 | 含义 |
|---|---|
| `PENDING_PAYMENT` | 已创建，等待支付 |
| `PAID` | 支付成功 |
| `CANCELLED` | 主动取消或超时取消 |

- 待支付订单有效期为 15 分钟。
- 只有 `PENDING_PAYMENT` 订单可以支付或取消。
- `PAID` 和 `CANCELLED` 均为 MVP 的终态。

### 4.6 模拟支付

- MVP 不接入微信、支付宝或银行卡。
- 支付接口模拟第三方支付成功通知。
- 同一个支付请求重复提交时，只允许第一次改变订单状态。
- 支付金额必须与订单金额一致。
- 已取消订单不能再次支付。

### 4.7 超时取消

- 订单创建 15 分钟后仍处于 `PENDING_PAYMENT`，系统自动将其改为 `CANCELLED`。
- 自动取消后必须释放座位。
- 同一条超时消息被重复处理时，不得重复修改订单或重复释放座位。
- 如果消息处理失败，系统必须能够重试或通过补偿任务最终完成取消。

## 5. 核心业务流程

### 5.1 正常预约与支付

```text
学生登录
  → 查询班次
  → 查看座位
  → 选择座位
  → 创建待支付订单
  → 临时锁定座位
  → 模拟支付成功
  → 订单变为 PAID
  → 座位变为 SOLD
```

### 5.2 超时取消

```text
创建待支付订单
  → 15 分钟内未支付
  → 触发超时取消
  → 订单变为 CANCELLED
  → 座位恢复 AVAILABLE
```

### 5.3 并发抢座

```text
多个学生同时选择同一座位
  → 系统进行最终一致的占座判定
  → 只允许一个订单创建成功
  → 其他请求返回“座位已被占用”
```

## 6. 订单状态机

```text
                    支付成功
PENDING_PAYMENT ─────────────→ PAID
       │
       │ 主动取消或超时
       ↓
   CANCELLED
```

状态转换规则：

| 当前状态 | 操作 | 目标状态 | 是否允许 |
|---|---|---|---|
| `PENDING_PAYMENT` | 支付 | `PAID` | 是 |
| `PENDING_PAYMENT` | 主动取消 | `CANCELLED` | 是 |
| `PENDING_PAYMENT` | 超时取消 | `CANCELLED` | 是 |
| `PAID` | 再次支付 | `PAID` | 幂等返回原结果 |
| `CANCELLED` | 支付 | — | 否 |
| `PAID` | 取消 | — | MVP 暂不支持 |

## 7. 必须满足的业务不变量

以下规则无论发生并发、重试还是服务重启都必须成立：

1. 同一班次的同一座位最多只能存在一个未取消订单。
2. 一个学生对同一班次最多只能存在一个未取消订单。
3. 已售座位数不能超过车辆总座位数。
4. 剩余座位数不能小于零。
5. 一个订单只能成功支付一次。
6. 一个订单只能有效释放一次座位。
7. 支付成功和超时取消不能同时成为最终结果。
8. 接口重试或消息重复消费不能改变已经确定的最终状态。

## 8. 非功能性需求

### 8.1 并发目标

以下是设计和测试目标，不是未经测试的简历数据：

- 测试场景：1,000 个用户同时抢 50 个座位。
- 成功的有效订单数量不得超过 50。
- 不允许出现重复座位。
- 不允许出现负库存。

### 8.2 性能目标

- 本地压测环境下，班次查询接口 P95 目标小于 300 ms。
- 本地压测环境下，创建订单接口 P95 目标小于 500 ms。
- 最终数据以实际压测报告为准，不提前写入简历。

### 8.3 安全

- 密码不得明文保存或输出到日志。
- 访问令牌、数据库密码和消息队列凭据不得硬编码到代码仓库。
- 管理员接口必须进行角色校验。
- 日志不得输出完整令牌或密码。
- 所有外部输入都必须进行参数校验。

### 8.4 可观测性

- 每个请求生成或传递 `traceId`。
- 关键操作记录结构化日志：创建订单、支付、取消和消息消费。
- 日志中包含订单号，但不包含敏感信息。
- 服务应提供健康检查接口。

### 8.5 可恢复性

- 消息消费失败后可以重试。
- 重复消息必须安全处理。
- 定时补偿任务能够扫描并处理遗漏的超时订单。
- 服务重启后，数据库中的订单和座位最终状态不能丢失。

## 9. MVP 明确不做的内容

- 真实支付渠道。
- 已支付订单退款。
- 优惠券和满减活动。
- 订单评价。
- 复杂排班算法。
- GPS 实时位置。
- 短信或邮件通知。
- 多人一次购买多个座位。
- 多租户和多学校支持。

这些功能只有在 MVP 完成并通过测试后才考虑。

## 10. 验收标准

### AC-01 注册与登录

- 使用新学号能够注册。
- 重复学号注册失败。
- 正确密码可以登录，错误密码不能登录。

### AC-02 班次查询

- 学生能查询尚未发车且允许预约的班次。
- 已停用或已发车班次不出现在可预约列表。

### AC-03 正常下单

- 可用座位可以创建订单。
- 订单初始状态为 `PENDING_PAYMENT`。
- 对应座位变为 `LOCKED`。
- 返回订单号和支付截止时间。

### AC-04 防止重复占座

- 两个用户同时预约同一班次的同一座位。
- 最多一个请求成功。
- 数据库中最多存在一个对应的有效订单。

### AC-05 模拟支付

- 待支付订单可以支付成功。
- 支付后订单状态为 `PAID`，座位状态为 `SOLD`。
- 重复支付请求返回相同结果，不重复更新数据。

### AC-06 超时取消

- 待支付订单超过 15 分钟后变为 `CANCELLED`。
- 座位恢复为 `AVAILABLE`。
- 重复处理取消事件不会再次释放座位。

### AC-07 并发测试

- 1,000 个并发用户抢 50 个不同座位。
- 最终有效订单不超过 50。
- 不存在重复座位和负库存。
- 测试结果形成可复现报告。

### AC-08 故障恢复

- 消费者处理消息时主动制造一次失败。
- 重试后订单能够完成取消。
- 重复消息不会造成错误状态。

- 未实现的功能不得写入简历。
- 未压测的数据不得作为项目成绩。
- 模拟支付必须明确说明为模拟支付。
- MQ 保证的是最终一致性时，不表述为数据库意义上的强一致事务。
- 使用缓存、分布式锁或消息队列时，必须说明其失败场景和最终兜底措施。
